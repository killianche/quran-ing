# Шрифты мусхафа: как это устроено и что нельзя ломать

> **Quran Ing (2026-10-03):** полноэкранного страничного мусхафа здесь нет —
> режим удалён по решению владельца (`MushafScreen`, `QcfMushafPage`,
> `mushafStrip`, `mushafFit`, `mushafFont` убраны). Всё про шрифты, нарезку по
> страницам и издания V1/V4 по-прежнему действует — этим рисуется лента
> аятов. Упоминания полноэкранного режима ниже — история an-Nur.

Основание бесплатного использования государственных арабских шрифтов именно в
коранических программах, официальные ссылки и правила атрибуции сохранены в
`docs/licenses/ARABIC_QURAN_FONTS.md`. Шрифты используются только для Корана;
постраничное подмножество не меняет контуры глифов, что проверяется пайплайном
ниже.

**TL;DR.** Текст мусхафа рисуется не буквами, а готовыми глифами-словами из
приватной области Unicode. Слово задаётся **парой** «PUA-код + шрифт», а после
нарезки — **тройкой** «код + шрифт + страница». Ошибка в этой связке не падает
и не подсвечивается: на экране будет красивый арабский, просто **не тот**.

**Имя для запроса:** «шрифты мусхафа», «постраничные шрифты», «почему кубики»,
«перегенерировать шрифты».

## Что где лежит

| Путь | Что это |
|---|---|
| `vendor/qcf4-fonts-woff2/` | 48 исходных шрифтов QCF V4 от King Fahd Complex, ~780 КБ каждый. **Вне `public`** — в рантайме не нужны, в пакете были лишними 36 МБ. Нужны, чтобы повторить нарезку. |
| `public/qcf4/fonts-page/NNN/FONT.woff2` | 797 постраничных подмножеств, ~71 КБ на страницу. Это то, что реально качает приложение. |
| `public/qcf4/pages/NNN.json` | Данные страницы: строки, слова, для каждого слова `char` (PUA-глиф) и `font`. |
| `scripts/build-page-fonts.py` | Генератор подмножеств с двойной проверкой. |
| `public/fonts/qpc-v4-tajweed-pNNN.woff2` | 604 официальных постраничных шрифта QPC V4 Tajweed в неизменённом формате COLR v0 + CPAL. Светлая тема выбирает штатную палитру 0, тёмная — штатную палитру 1: основной штрих становится соответственно чёрным или белым, а правила таджвида сохраняют свои цвета. Не преобразовывать в COLR v1 и не добавлять SVG-in-OpenType: на проверенном WKWebView COLR v1 стал монохромным, а SVG не смог надёжно менять базовый штрих по теме. |
| `public/tajweed/pages/NNN.json` | Точная постраничная разметка цветного мусхафа: строка, аят, позиция и PUA-код. Это единый runtime-источник и для полноэкранной страницы, и для ленты аятов: лента больше не загружает общий 3,3-МБ словарь всего Корана. |
| `scripts/gen/fetch-tajweed-data.ts` | Получает Tajweed V4 с `mushaf=19` и воспроизводит глифы и 604 страницы. |

## Как перегенерировать

```bash
python3 scripts/build-page-fonts.py
```

Требует `fontTools` и `brotli`. Идемпотентен: свежие файлы пропускает.
Отдельные страницы — `python3 scripts/build-page-fonts.py 77 90`.
Только проверить готовое — `python3 scripts/build-page-fonts.py --check`.

## 🔴 Обязательный порядок после правки данных мусхафа

Если менялись `public/qcf4/pages/*.json` или исходные шрифты:

1. `python3 scripts/build-page-fonts.py` — перегенерировать подмножества.
2. `npm test` — группа «Шрифты мусхафа: подмножества сгенерированы полностью»
   проверит, что для каждой страницы есть ровно те файлы, которые она просит.
3. `npm run build`
4. **`npx cap sync`** — иначе в iOS и Android останутся старые файлы.
5. Проверить на симуляторе, что арабский виден.

**Шаг 4 однажды уже забыли.** В `ios/` и `android/` лежали старые 48 шрифтов, а
постраничных не было вовсе: код просил `/qcf4/fonts-page/NNN/`, и на телефоне
аяты остались бы пустыми навсегда. В вебе всё работало — проблема видна только
в нативной сборке.

## Цветной шрифт в полноэкранном мусхафе

В меню «Оформление → Шрифт страницы» доступны «Обычный» и «Цветной таджвид».
Это два постраничных лица одного мединского издания, а не свободная замена
`font-family`: цветной режим использует собственные коды и `line_number` из
Quran Foundation Tajweed V4 (`mushaf=19`). Декоративные заголовки сур и басмала,
которых нет в Tajweed API, остаются QCF.

Перегенерация цветного набора:

```bash
npx tsx scripts/gen/fetch-tajweed-data.ts --skip-fonts --force-glyphs
```

Для восстановления/полного обновления всех 604 официальных шрифтов:

```bash
npx tsx scripts/gen/fetch-tajweed-data.ts --force-fonts --skip-glyphs
npm run build
npx cap sync ios
```

После загрузки бинарники не модифицировать. При их замене повысить
`TAJWEED_FONT_VERSION` в `src/hooks/useTajweedFont.ts`, иначе WKWebView может
оставить старый нерабочий файл в кэше.
Несмотря на каталог `colrv1` в CDN Quran Foundation, текущий официальный WOFF2
содержит COLR версии 0, CPAL с шестью палитрами и не содержит `SVG `. Именно
этот файл сохраняет цветные слои в WKWebView; самодельная конвертация COLR
v0→v1 привела к монохромному fallback. Исторические скрипты
`patch-tajweed-default-palette.py`, `upgrade-tajweed-colr-v1.py` и
`add-svg-in-ot.py` к runtime-набору не применять.

### Подтверждённая матрица iOS

Проверено владельцем на физическом iPhone 2026-08-17, а не только в браузере
или симуляторе:

| Runtime-вариант | Основной штрих по теме | Цвета правил таджвида | Решение |
|---|---|---|---|
| SVG-in-OpenType с `context-fill` | остаётся чёрным на тёмной теме | сохраняются | запрещён |
| Самодельный COLR v0 → v1 | CSS-fallback мог дать нужный базовый цвет | исчезают, текст становится монохромным | запрещён |
| Официальный COLR v0 + CPAL без изменений | palette 0 — чёрный, palette 1 — белый | сохраняются полностью | единственный рабочий путь |

Runtime-инварианты:

- `src/lib/tajweedPalette.ts`: `BASE_PALETTE_BY_MODE = { light: 0, dark: 1 }`;
- `src/hooks/useTajweedFont.ts`: версия кэша начинается с
  `official-colrv0-cpal-`;
- `.tajweed-theme-ink` задаёт только монохромный fallback, а реальными цветами
  управляют `COLR/CPAL` и CSS `font-palette`;
- после `npx cap sync ios` проверить на физическом iPhone светлую и тёмную темы:
  базовые буквы должны стать соответственно чёрными и белыми, а зелёные,
  синие, розовые, оранжевые и остальные цвета правил должны остаться видимыми.

Первые две страницы в API физически используют строки 9–15 и 10–15; генератор
снимает семь пустых верхних строк, чтобы совпасть с компактными QCF JSON. Это
зафиксировано проверкой всех 604 страниц в `npm test`.

## Три правила, которые нельзя нарушать

### 1. Семейство обязано нести номер страницы

```ts
qcfPageFamily('QCF4_Hafs_06', 77)  // → 'QCF4_Hafs_06_p77'
```

QCF V4 переиспользует одни и те же PUA-коды в разных шрифтах: `0xF103` в
`Hafs_01` и в `Hafs_06` — **разные слова**. Подмножества одного шрифта для
разных страниц тоже пересекаются по кодам.

Если назвать их одинаково, браузер сложит все `@font-face` с этим именем в одно
семейство и на пересекающемся коде отдаст глиф не той страницы — **чужое слово
внутри аята**. Ни типы, ни сборка этого не увидят.

Поэтому же у слова есть поле `page`: его проставляет `hydratePage` при загрузке.
Аят на стыке страниц берёт слова с двух — одного номера на аят не хватает.

### 2. Кубики недопустимы

У PUA-кодов нет запасного глифа ни в одном системном шрифте. «Показать текст,
пока шрифт не приехал» означает ряды пустых квадратов на месте аята — это
выглядит как испорченный Коран.

Поэтому текст рисуется **только** после подтверждённой загрузки
(`useQcfFont` → `ready`), а до этого на его месте `ArabicSkeleton`. Если
загрузка не удалась — `FontErrorBanner` с повтором, но не текст.

`font-display: block` в правиле остаётся страховкой: пустая строка лучше кубиков.

### 3. Готовность шрифта проверяется по статусу FontFace

```ts
const ok = faces.length > 0 && faces.every(f => f.status === 'loaded');
```

**Не через `document.fonts.check(...)`.** Без второго аргумента `check()`
спрашивает, нарисуется ли **пробел**, а в подмножестве страницы бывает
один-единственный PUA-глиф без пробела. Загруженный шрифт считался бы
сломанным, и плашка об ошибке висела бы над живым текстом.

## Почему нарезали по страницам

QCF V4 раздаётся 48 файлами по ~780 КБ, каждый содержит 2073 глифа. Странице
нужно около 140 из них. На открытие уходило в среднем 0.89 МБ, местами 1.78 МБ.
Худший случай — служебные шрифты: страница 77 тянула `QCF4_Hafs_01` весом
924 КБ **ради одного глифа** с названием суры.

После нарезки: 2.26 МБ → 84 КБ (3.6%). Время до арабского на живом сервере —
0.8–2 с вместо 10–20.

## Почему это безопасно для сакрального текста

Сабсеттинг не рисует и не меняет глифы — он выбрасывает из бинарника
неиспользуемые. Формы букв остаются те же байты, что дал King Fahd Complex.

«Должно быть безопасно» для мусхафа не годится, поэтому генератор проверяет
каждую страницу дважды и падает при первом расхождении:

1. **Покрытие** — cmap подмножества содержит все коды, которые есть на странице.
2. **Тождество** — контур и ширина каждого глифа сверяются с оригиналом по хешу
   записи пера.

Прогон по всем 604 страницам: расхождений нет. Дополнительно сверено в браузере —
16 слов с 4 разных страниц отрисованы подмножеством и оригинальным шрифтом,
ширина и высота совпадают до сотых.

## Что ещё держит скорость

Эти вещи легко случайно откатить, поэтому они перечислены здесь:

- **Шрифт просят только аяты вблизи экрана** (`useNearViewport`). Сура
  монтируется целиком, и без этого Ан-Ниса разом запрашивала 32 подмножества —
  файл первого экрана приходил вместе с последними.
- **Первые `EAGER_AYAHS` от места чтения просят сразу**, минуя наблюдатель:
  при монтировании длинной суры его вердикт приходил через две секунды **после**
  того, как шрифт уже загрузился.
- **Шрифт первой страницы заказывается до готовности ленты** — номер страницы
  известен из таблицы `mushafPages` без сети.
- **Лента отдаёт начало суры**, не дожидаясь остальных страниц (только когда
  читают сверху).
- **Датасет альтернативных начертаний (3.9 МБ) не качается**, пока выбран
  мусхаф. Раньше тянулся при каждом открытии суры и забивал канал.
- **Соседние страницы мусхафа предзагружаются** — перелистывание без скелета.
- **Цветной шрифт открытой страницы стартует в первом рендере**, до загрузки
  JSON, по фиксированному PUA sample. Соседние цветные страницы и их JSON
  прогреваются следом; открытие «Оформления» заранее прогревает текущую.

## Кэш на сервере

Правила в `/etc/caddy/Caddyfile`, блок `l.asrbook.ru`: кэш по **расширению**,
а не по папке. Раньше правила покрывали только `/assets`, `/fonts`, `/audio`, и
шрифты мусхафа уходили вообще без `Cache-Control` — браузер перекачивал их при
каждом открытии суры.

Две грабли, на которые уже наступили:

- **Матчеры Caddy соединяют `path` через И, а не ИЛИ.** Несколько строк `path`
  в одном именованном матчере дают невыполнимое условие. Все расширения — одной
  строкой.
- **Правку якорить по границам блока сайта**, а не по первому совпадению текста:
  на сервере несколько сайтов с одинаковыми правилами, и патч ушёл не туда.
  Проверять `caddy adapt`, а не только `caddy validate`.

## Разведка по добавлению шрифтов (30.08.2026)

Владелец попросил добавить в полноэкранный режим «шрифт мусхафа мединский,
современный».

### Запрошенное уже стоит основным

**QCF V4 — это и есть мединский мусхаф издания 1441 г.х.**, каллиграфия
Усмана Таха, King Fahd Complex. Подтверждено `public/qcf4/LICENSE.md` в самом
проекте, а не памятью модели. V4 описывается как улучшенная редакция V2 (2013).

**Есть ли издание новее — не проверено.** Официальные `qurancomplex.gov.sa`,
`fonts.qurancomplex.gov.sa`, `dm.qurancomplex.gov.sa` с сервера разработки
недоступны: имя резолвится (66.9.131.70), соединение не устанавливается.
Поиск по вебу издания новее 1441 с официальным шрифтом не показал, но это
«не нашли», а не «нет». Считать вопрос открытым до проверки с сети, откуда
сайт KFGQPC отвечает.

### Что лежит в проекте и не используется

| Файл | Объём | Состояние |
|---|---|---|
| `public/qcf-text-fonts/HafsNastaleeq.woff2` | 89 КБ | ни одного `@font-face`, ни одной ссылки в `src/` |
| `public/qcf-text-fonts/PDMS_Saleem.woff2` | 66 КБ | `@font-face` есть, но режим IndoPak удалён — ни один вариант на него не ссылается |

Реестры шрифтов разные, и это легко упустить: `src/lib/mushafFont.ts` —
полноэкранный режим, три варианта; `src/lib/typography.ts` `ALL_ARABIC_FONTS`
— лента, четыре варианта. Добавляя шрифт, проверь оба: они не связаны.

### QCF V1 «Мадани 1405» — подключён 31.08.2026

Третий вариант шрифта в полноэкранном режиме, рядом с QCF V4 и цветным
таджвидом. Шрифты уже лежали в пакете, новых байтов начертания не потребовали;
добавилась только разметка `public/qcf1/pages/NNN.json` — 604 файла, 9,6 МБ.

`scripts/build-page-fonts.py` здесь **не применим**: он режет 48 общих шрифтов
V4 по страницам, а V1 раздаётся постранично изначально.

Честная оговорка: V1 — издание **1405 г.х.**, то есть старше нынешнего. Это
«ещё один мединский», но не «более современный».

### 🔴 Ловушка нумерации изданий в API quran.com

**`mushaf=1` — это QCF V2, а `mushaf=2` — QCF V1.** Не интуитивно и легко
перепутать. Источник: enum в `types/QuranReader.ts` репозитория
`quran/quran.com-frontend-next` (`QCFV2 = 1, QCFV1 = 2, Indopak = 3,
UthmaniHafs = 4, KFGQPCHAFS = 5, Tajweed = 11, QCFTajweedV4 = 19`),
подтверждено экспериментом: на странице 3 у `mushaf=1` и `mushaf=2` расходятся
строки 8–10.

Взять `code_v1` с `mushaf=1` — получить правильные глифы на неправильных
строках. Это ровно та тихая ошибка, о которой предупреждает правило №2 выше:
на экране красивый арабский, просто не тот.

### Отвергнуто

- **QCF V2** — 78 МБ ради начертания, улучшенной редакцией которого V4 и
  является. Отдача не оправдывает вес.
- **IndoPak в любом виде** — у него своя пагинация (13/15/16 строк вместо 604
  мединских страниц) и другой правообладатель. Это не «ещё один шрифт», а
  вторая модель страницы внутри приложения.
- **Warsh, Qaloon, Douri, Sousi, Shuba** — это другие риваяты, то есть другой
  кораничный текст, а не другое начертание. Под видом «шрифта» не добавлять.

### Как устроен V1 и чем отличается от V4

Отличие одно, но из него растёт вся разница в коде:

| | V4 | V1 |
|---|---|---|
| Нарезка шрифтов | 48 общих шрифтов, нарезаны по страницам | шрифт сам по себе постраничный |
| Семейство слова | `${имяШрифта}_p${страница}` | просто `QCF1_P{NNN}`, без суффикса |
| Файл | `/qcf4/fonts-page/{NNN}/{шрифт}.woff2` | `/qcf1/fonts-woff2/QCF_P{NNN}.woff2` |
| Поле `font` у слова | у каждого слова | только у `surah_header` и `bismillah` (`QCF1_BSML`) |
| Заголовок суры | один глиф | два глифа: «سورة» + название |
| Басмала | один глиф | три глифа (у одной страницы четыре) |

Издание записано **в самих данных** (`edition` на уровне страницы) и явно
проходит через загрузку, кэш и сборку имени семейства. Выводить издание из
префикса имени шрифта нельзя: это прячет правило внутри строки.

🔴 **Кэш страниц обязан ключеваться изданием.** Страница 106 существует в
обоих изданиях. Кэш без издания в ключе отдал бы данные V4 под шрифты V1 —
на экране красивый арабский, просто чужой. Ни типы, ни сборка этого не поймают.

### История: как искали заголовки сур (30–31.08.2026)

Раздел стоит читать перед тем, как добавлять четвёртое издание: половина
времени ушла на гипотезу, которая оказалась неверной.

**Что остановило работу 30.08.** На страницах с началом суры API не отдаёт
двух строк — заголовка и басмалы (проверено на странице 106: приходят строки
1–5 и 8–15). То же самое у `mushaf=1`, так что переход на V2 не помог бы.

**Неверная гипотеза.** Считали, что в `QCF_BSML.woff2` лежит по глифу на
название суры и нужна таблица «сура → код». Вскрытие шрифта показало другое:

- Названий сур в нём нет вовсе. Настоящие глифы — куски басмалы, таʿаввуз,
  «قَالَ تَعَالَىٰ», «صدق الله العظيم» и орнаменты.
- 🔴 **Обычные арабские коды U+06xx в нём ведут на пустую прямоугольную
  заглушку**, при этом в `cmap` они присутствуют. То есть проверка «есть ли
  символ в таблице кодировки» здесь **врёт**: `cmap` отвечает «есть», а на
  экране кубик. Сверять надо контур глифа. Это общее правило для шрифтов
  такого рода, не частность V1.

**Что закрыло вопрос.** Репозиторий `quran/quran.com-images` — оригинальный

**Две ловушки, каждая даёт молчаливо неверную страницу Корана:**

1. **Коды заголовков нельзя считать формулой.** `0xFB8C + N` верна только для
   37 сур из 114: на суре 38 в шрифте разрыв (U+FBB1 → U+FBD3).
2. **Пробел в нумерации строк не говорит, что рисовать.** На странице 187
   (сура 9, басмалы нет) и на странице 208 пропущено по одной строке, но на
   первой это заголовок, а на второй — басмала, потому что заголовок суры 10
   остался на предыдущей странице.

**Смещение на первых страницах.** У страниц 1 и 2 API нумерует строки с
девятой и десятой. Смещение ровно +7 у обеих. Прежняя догадка «нормализовать
по минимуму на странице» **неверна**: на первой странице минимум даёт строку
1, которая на самом деле занята заголовком суры, и строки наехали бы друг на
