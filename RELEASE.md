## Что где может выполняться

Ограничение ровно одно, и оно не обходится никакими доступами: **архив
собирает Xcode, а Xcode работает только под macOS.**

| Что | Где | Почему |
|---|---|---|
| Сборка веба, тесты, гарды, `cap sync`, предполётная проверка | где угодно, в том числе на сервере разработки | обычный Node |
| **Сборка и подпись `.app`/`.ipa`** | **любая машина с macOS** | нужен Xcode |
| **Загрузка сборки в App Store Connect** | оттуда же, где собрали | `xcodebuild -exportArchive` с `destination=upload` |
| Метаданные карточки, скриншоты, выбор сборки, отправка на ревью, TestFlight | где угодно | App Store Connect API |

Ключевое слово во второй строке — **любая**. Это не обязательно ваш ноутбук:
арендованный macOS-раннер GitHub подходит ровно так же, и тогда к ноутбуку
никто не подходит. Именно это и делает `.github/workflows/ios-release.yml`.

Сервер разработки, где идёт эта работа, — Ubuntu (`350672.fornex.cloud`).
Xcode сюда не ставится: он не существует под Linux. Это не вопрос прав или
усилий.

Пароль Apple Account при этом не нужен и не запрашивается: по правилам проекта
(`CLAUDE.md`, §0.2) пароль, коды 2FA и recovery key не просят и в репозитории
не хранят. Нужен другой, узкий и отзываемый доступ — ключ API, см. ниже.

## Путь без ноутбука: сборка в облаке

Файл `.github/workflows/ios-release.yml` собирает архив на macOS-машине GitHub
и выгружает его в App Store Connect. Xcode при этом установлен у GitHub, а не
у нас — именно поэтому путь работает, когда доступа к Mac нет.

### Что нужно один раз

**1. Репозиторий на GitHub.** Приватный. Ограничения проверены: самый большой
файл проекта — 4,2 МБ (GitHub блокирует от 100 МБ), под контролем версий
0,25 ГБ в 3656 файлах. История весит 1,2 ГБ — заливается долго, но заливается.

**2. Три секрета** в Settings → Secrets and variables → Actions:

| Имя | Что класть |
|---|---|
| `ASC_ISSUER_ID` | Issuer ID, общий на команду |
| `ASC_KEY_ID` | Key ID выпущенного ключа, 10 символов |
| `ASC_KEY_P8` | содержимое файла `AuthKey_XXXXXXXXXX.p8` целиком, вместе со строками `-----BEGIN PRIVATE KEY-----` |

Где взять — раздел «Доступ к App Store Connect» ниже.

### Как запускать

Actions → **iOS release** → Run workflow. Переключатель `upload`:

- **выключен** (по умолчанию) — только собрать и проверить, ничего никуда не
  уйдёт. Так проверяется первый запуск.
- **включён** — собрать и выгрузить в App Store Connect.

Сначала прогон с выключенным `upload`. Он проходит те же проверки, что и
сервер разработки, затем собирает архив — то есть доказывает, что подпись
получена и сборка состоялась, ничем не рискуя.

### Проверено на практике 30.08.2026

Сценарий отработал полностью: `Upload succeeded` → `Uploaded App` →
`** EXPORT SUCCEEDED **`. Путь занял четыре запуска, и каждый отказ дал факт,
которого не было в документации:

| Запуск | Чем кончился | Что выяснилось |
|---|---|---|
| #1, без выгрузки | успех | имена флагов `-authenticationKey*` верны; `-allowProvisioningUpdates` получает сертификат по ключу |
| #3, с выгрузкой | `Cloud signing permission error` | ключа с ролью App Manager не хватает — нужен **Admin** |
| #4, ключ Admin | отказ Apple на проверке | `macos-15` несёт SDK iOS 18.5, а Apple требует **iOS 26 и новее** |
| #5, образ `macos-26` | успех | Xcode 26.6, SDK iOS 26.5 |

Отсюда шаг «Версия Xcode и SDK» в начале сценария: расхождение по SDK теперь
видно до сборки, а не через десять минут в отказе Apple.

**Что стоит помнить.** Архив подписывается сертификатом разработки
(`Apple Development: Created via API`), а сертификат распространения Xcode
применяет уже на экспорте. Это штатный порядок, пугаться его в логе не нужно.

**Если облачная подпись однажды откажет** (например, исчерпан лимит
сертификатов распространения), есть обходной путь без Mac: приватный ключ и
CSR генерируются через `openssl`, сертификат создаётся запросом к App Store
Connect API. Так работает `fastlane match`. Пишется по факту отказа.

**Альтернатива, если GitHub Actions окажется неудобен** — Xcode Cloud,
собственный сервис Apple, встроенный в App Store Connect. Ему тоже нужен
подключённый git-репозиторий.

## Запасной путь: шаги на Mac

Нужен, только если облачная сборка не подошла. Предполагается, что
репозиторий на Mac синхронизирован с этим состоянием.

**1. Прогнать полную проверку.** Одна команда делает всё: тесты, сакральный
гард, сборку, `cap sync` и предполётную проверку.

```bash
npm run ios:release-check
```

Ожидаемый хвост вывода — `35/35 проверок пройдено`. Если что-то красное,
дальше не идти: именно это и должен ловить гард.

**2. Открыть проект.**

```bash
open ios/App/App.xcodeproj
```

**3. Архив.** В верхней панели выбрать назначение `Any iOS Device (arm64)` —
не симулятор, иначе пункт Archive неактивен. Затем `Product → Archive`.

**4. Загрузка.** Открывшийся Organizer → выбрать свежий архив → `Distribute App`
→ `App Store Connect` → `Upload`. Дождаться, пока Apple обработает сборку
(обычно минуты, иногда до часа) — до этого она не появится в списке.

**5. Отправка на ревью.** В App Store Connect создать версию `1.2`, выбрать
обработанную сборку `1.2 (4)`, вставить «Что нового» из `APP_STORE.md`,
отправить. Этот шаг можно снять с человека — см. следующий раздел.

Архив полезно сохранить рядом с прошлыми: `app-store/archive/`. В git он не
попадёт — каталог в `.gitignore` как артефакт сборки (каждый весит за 200 МБ).

## Доступ к App Store Connect

Ключ API нужен обоим путям: облачной сборке он даёт получить подпись и
выгрузить архив, а сверх того позволяет вести карточку и отправлять версию на
ревью удалённо.

### Как выпустить ключ

1. App Store Connect → **Users and Access** → вкладка **Integrations** →
   **App Store Connect API** → **Team Keys**.
2. Кнопка **+**, имя произвольное (например `an-Nur release`).
3. Роль — **Admin**. Это проверено на практике, а не выбрано «на всякий
   случай»: с ролью App Manager сборка доходит до архива, а на экспорте падает
   с `Cloud signing permission error` и `No signing certificate "iOS
   Distribution" found`. Apple требует Admin именно для облачной подписи
   распространения — ключ с меньшими правами не может ни создать, ни
   использовать сертификат распространения.
   Для чтения состояния и правки карточки App Manager действительно хватает,
   но для сборки — нет.
4. Скачать файл `AuthKey_XXXXXXXXXX.p8`. **Apple даёт скачать его один раз.**
5. Записать рядом два значения с той же страницы: **Issuer ID** (общий на
   команду, вида `69a6de70-…`) и **Key ID** (10 символов, он же в имени файла).

### Что передать

Три вещи: файл `.p8`, Issuer ID, Key ID. Файл кладётся в `secrets/` — каталог
целиком в `.gitignore`, как и любые `*.p8`; проверено, git его не видит.

Пароль Apple Account, коды двухфакторной аутентификации и recovery key
передавать не нужно и нельзя.

### Проверка доступа

Первая команда — только чтение, ничего не меняет:

```bash
ASC_ISSUER_ID=<issuer id> \
ASC_KEY_ID=<key id> \
ASC_KEY_PATH=secrets/AuthKey_XXXXXXXXXX.p8 \
npm run asc:status
```

Она печатает приложения команды, версии и загруженные сборки. Если приложение
`ru.annur.quran` в списке — доступ настроен верно.

### Если ключ скомпрометирован

Отозвать там же, в Integrations, кнопкой **Revoke**. Действует немедленно.
Выпустить новый — минута.

## Что останется сделать после появления доступа

Команды поверх готового клиента (`scripts/appstore/asc-client.mjs`) пишутся
после первой удачной проверки доступа, а не вслепую: состав полей у версий и
сборок Apple меняла не раз, часть атрибутов помечена deprecated. Поэтому
`asc:status` печатает атрибуты **как есть** — по её выводу видно фактические
имена полей, и уже на них строятся команды правки. Писать их сейчас наугад
означало бы выдумывать имена эндпоинтов, чего делать нельзя.

Порядок работ, когда ключ появится:

1. `npm run asc:status` — убедиться, что доступ есть и приложение видно.
2. По фактическому ответу дописать команду обновления «Что нового» и выбора
   сборки.
3. Отправка на ревью — последним шагом, отдельной командой с явным
   подтверждением: это действие видно снаружи и его нельзя отменить незаметно.
